# 架构与技术栈选型

**项目**：社区任务与二手交易 App（需求文档 V1.4.1）
**日期**：2026-10-09 起草，2026-10-10 定稿（ADR-003 确认 uni-app X、ADR-004 修订动态轮询）
**结论先行**：模块化单体架构 + Java 17 / Spring Boot 3 + MySQL 8 + Redis 7 后端，Vue 3 管理后台，App 端 uni-app X（一套代码双端，W1 技术验证）。本文 5 条 ADR 记录每个决策的"为什么"和"放弃了什么"。

---

## 一、约束条件（选型从这里出发，不从技术偏好出发）

| 约束 | 来源 | 对选型的影响 |
|------|------|--------------|
| 1 万注册、日活 500～2000 | 需求 1.3 | 并发极低，任何架构的性能都不是问题，**复杂度才是敌人** |
| 单服务器 + 自建数据库 + OSS/CDN | 需求 1.3 | 运维能力有限，组件越少越好 |
| 周期 10～12 周、后端 1～2 人 | 需求 10.4/10.5 | 框架要"开箱即用"，少造轮子 |
| 只做信息撮合、无支付、无实时 IM | 需求 4.2/4.3/4.5.4 | 不需要分布式事务、不需要长连接服务 |
| 先发后审（论坛）+ 机审 + 限频 | 需求 4.7 | 需要对接外部 API（内容安全、短信），选生态成熟的 |
| 开发者在学 Java 全栈 | 学习路径 | **后端选 Java 系，学以致用**（这是最重要的现实约束） |

## 二、架构模式：模块化单体（ADR-001）

**决策**：单进程 Spring Boot 应用，按业务模块分包（user / task / trade / forum / message / ads / audit），模块间只通过 Service 接口调用。

| 选项 | 适合 | 不适合本项目的原因 |
|------|------|---------------------|
| **模块化单体（选定）** | 小团队、边界清晰、单机部署 | 无 |
| 微服务 | 多团队并行、独立扩容需求 | 1～2 个后端维护 8 个服务是灾难；分布式事务、链路追踪、服务发现的复杂度全是纯成本 |
| Serverless | 流量极不均匀 | 国内云厂商冷启动 + 调试体验差，备案合规也绕 |

**放弃了什么**：未来某模块独立扩容的能力。**换来了什么**：一个 jar 包、一台服务器、一条日志链路、零分布式问题。
**演进触发器**（到这些量级再谈拆分）：日活 > 2 万、单表 > 500 万行、或团队 > 5 个后端。

## 三、技术栈清单

### 后端（ADR-002）

| 层 | 选型 | 理由 | 备选（何时换） |
|----|------|------|----------------|
| 语言/框架 | Java 17 + Spring Boot 3.3 | 生态最全（短信/机审/广告 SDK 全有官方 SDK）、与学习路径一致 | — |
| ORM | MyBatis-Plus | 国内主流、学习资料多、CRUD 零 SQL 起步 | JPA（若更熟） |
| 数据库 | MySQL 8.0 | 免费、资料多、云厂商托管成熟 | PostgreSQL（无强需求不换） |
| 缓存 | Redis 7 | 验证码、短信限频、JWT 会话、热评缓存、点赞防重，全靠它 | — |
| 鉴权 | JWT + Redis（登录态/黑名单） | 无状态易水平扩展；封禁/注销走 Redis 黑名单 | Session（单体下也行，但 JWT 迁移成本低） |
| 定时任务 | Spring Task | 超期自动下架、备份触发，量小无需 XXL-JOB | XXL-JOB（任务多再上） |
| 文件 | 阿里云 OSS + CDN，服务端签名直传 | 服务器不经手大文件 | 腾讯云 COS 同级 |
| 构建 | Maven | 国内资料最多 | Gradle（无所谓） |
| 文档 | SpringDoc（Swagger） | 接口文档自动生成，App 端联调靠它 | — |

**明确不用**：微服务框架、消息队列（当前无异步解耦需求，定时任务量级用不着）、WebSocket（站内信是拉取式，见 ADR-004）。

### App 端（ADR-003，已定：uni-app X）

**决策（2026-10-10 确认）**：采用 **uni-app X**——DCloud 的新一代方案，UTS 语言编译为 Kotlin/Swift 原生渲染，一套代码出 iOS + Android 双端。

| 对比项 | uni-app X（选定） | 普通 uni-app | 原生双端 |
|--------|-------------------|--------------|----------|
| 渲染/性能 | 编译为原生（Kotlin/Swift），接近原生性能 | WebView/vue 渲染，信息流场景够用 | 原生上限 |
| 生态/插件 | 较新，插件市场在成长中，资料少 | 成熟，插件海量 | 全部自己写 |
| 语言 | UTS（类 TypeScript） | Vue | Swift + Kotlin |
| 团队要求 | 1 人即可出双端 | 1 人即可出双端 | 2 人双倍工期 |

**选 X 放弃了什么**：普通 uni-app 海量的成熟插件与踩坑资料。**换来了什么**：原生渲染性能、不用维护 WebView 兼容性、技术栈更接近未来方向。

**风险与缓解（必须执行）**：

| 风险 | 缓解措施 |
|------|----------|
| 广告 SDK（穿山甲/优量汇）在 X 下的 uts 插件成熟度未知 | **W1 做 3 天技术验证**：跑通穿山甲/优量汇 demo + uni-ad，跑不通则降级到普通 uni-app（页面语法同源，迁移成本可控） |
| OSS 直传、图片压缩等基础能力插件可用性 | 同上，一并纳入 3 天验证清单 |
| X 迭代快、坑多、资料少 | 锁定一个正式版版本号开发，不追新；遇到坑优先查 DCloud 官方论坛 |
| iOS 审核对 X 编译产物的兼容性 | 用官方最新正式版打包，提交前在真机完整回归 |

**技术验证清单（W1，3 天内完成，全部通过则继续 X，任一失败降级普通 uni-app）**：
1. 穿山甲或优量汇 uts 插件跑通 Banner + 插屏；
2. OSS 签名直传（图片）跑通；
3. 双列瀑布流 + 图片加载滚动无明显卡顿；
4. 打包 iOS 真机安装运行。

### 管理后台（Web）

Vue 3 + Vite + Element Plus + Axios + ECharts（数据看板）。X 的 UTS 语法类 TypeScript，与管理后台的 Vue/TS 同源，学习不冲突。

### 第三方云服务（全部按量付费，零自建）

短信（阿里云/腾讯云）、内容安全机审（腾讯云/阿里云）、广告（穿山甲/优量汇）、云备份（OSS 跨区域复制或快照）。

## 四、部署架构

单台 4C8G 云服务器（中国大陆，备案前提）：

- Nginx：HTTPS 终结、反向代理、静态资源
- Spring Boot jar：systemd 托管，单实例
- MySQL 8 + Redis 7：同机部署但用 systemd/cgroup 做资源限制（避坑清单 M 项），或 MySQL 用最低配云托管（多几十元/月，**备份和恢复演练省很多事，预算允许优先这个**）
- OSS + CDN：媒体文件
- 备份：mysqldump 每日全量 → OSS，**每月做一次恢复演练**

## 五、ADR 决策记录

### ADR-001：采用模块化单体，拒绝微服务
- **状态**：Accepted
- **背景**：日活 500～2000，后端 1～2 人，10～12 周交付。
- **决策**：单进程 Spring Boot，按业务模块分包，模块间 Service 接口调用、禁止跨模块直查表。
- **后果**：获得——部署/调试/备份全部最简；失去——模块级独立扩容；回退方案——模块分包为未来拆服务留了缝，触发条件见第二节。

### ADR-002：后端选 Java / Spring Boot 而非 Node / Go
- **状态**：Accepted
- **背景**：开发者在学 Java 全栈；需要对接短信、机审、广告 SDK 等大量国内云服务。
- **决策**：Java 17 + Spring Boot 3.3 + MyBatis-Plus。
- **后果**：获得——与学习路径一致、国内云服务 SDK 和资料最全；失去——Go 的部署轻量与并发性能（本场景用不上，纯放弃无损失）。

### ADR-003：App 端采用 uni-app X
- **状态**：Accepted（2026-10-10 确认）
- **背景**：需求文档原假设 iOS/Android 各 1 人；实际 1 人全栈，需一套代码出双端。候选：原生双端、普通 uni-app、uni-app X。
- **决策**：采用 uni-app X（UTS 编译原生渲染，一套代码双端）。配套约束：①W1 先做 3 天技术验证（广告 SDK 插件、OSS 直传、滚动性能、iOS 真机），任一失败降级普通 uni-app；②锁定正式版版本号开发，不追新。
- **后果**：获得——原生渲染性能、一套代码双端、UTS 与管理后台 TS 同源；失去——成熟插件生态与踩坑资料（靠 3 天验证前置排雷）；需求文档 10.5 人力表已同步改为"App 1 人（uni-app X）"。

### ADR-004：站内信用"动态轮询"而非 WebSocket 长连接
- **状态**：Accepted（2026-10-10 修订：固定 60 秒 → 分场景动态轮询）
- **背景**：站内信定位是异步留言（V1.2.1 已定不做实时聊天），推送通知在二期。固定 60 秒轮询在"双方都在会话页"场景下延迟偏高，体验不足。
- **决策**：分场景动态轮询——
  | 场景 | 策略 |
  |------|------|
  | 会话页内（正在对话） | 5 秒轮询该会话新消息 |
  | App 前台其他页面 | 30 秒轮询未读数（只查 Redis 计数器） |
  | 打开消息中心 / 进入会话 | 立即拉取一次 |
  | App 切后台 | 停止轮询（省电） |
- **成本核算**：2000 日活 × 前台日均 30 分钟，30 秒轮询全天约 17 万次请求，平均 2 QPS 量级，单机毫无压力——轮询的瓶颈从来不是服务器，是手机电量（动态策略已兼顾）。
- **后果**：获得——无长连接服务、无重连/心跳问题；正在对话的双方 5 秒级近似实时；失去——切后台时无提醒（二期接厂商推送通道解决，收到推送后 App 仍拉取数据，不做自建长连接）。

### ADR-005：鉴权用 JWT + Redis 黑名单，而非纯 Session
- **状态**：Accepted
- **背景**：客户端是 App（token 管理）+ 后台（管理员），有封禁/注销（需求 4.1.3）需即时踢下线。
- **决策**：登录发 JWT（App 30 天 / 后台 2 小时 + 刷新）；封禁/注销时把用户 ID 写入 Redis 黑名单，网关过滤器统一拦截。
- **后果**：获得——App 端 token 管理简单、封禁即时生效；失去——纯无状态的极简（多一个 Redis 依赖，但 Redis 反正要装）。

## 六、后端目录结构建议（模块化单体落地）

```
backend/
└── src/main/java/com/shequ/
    ├── common/          # 统一返回体、全局异常、鉴权过滤器、工具类
    ├── config/          # Redis、OSS、Swagger、安全配置
    ├── module/
    │   ├── user/        # 注册三步、登录、资料、封禁、拉黑
    │   ├── task/        # 任务发布/列表/详情
    │   ├── trade/       # 二手发布/审核/列表/收藏/联系方式
    │   ├── forum/       # 帖子/评论/点赞/热评/公告/举报
    │   ├── message/     # 三类会话站内信、消息中心
    │   ├── ads/         # 广告位配置、曝光/点击上报
    │   └── analytics/   # 5 个埋点事件、看板数据
    └── job/             # 定时任务：超期下架、备份触发
```

模块间规则：**只允许调用对方模块的 Service 接口，禁止跨模块直接查表**——这是未来能拆微服务的唯一保障，也是模块化单体的全部纪律。

## 七、技术债与演进路线（提前写好触发条件）

| 触发条件 | 动作 |
|----------|------|
| 日活 > 2 万 或 核心表 > 500 万行 | MySQL 读写分离或迁云托管高配 |
| 需要真正的推送 | 接厂商推送通道（APNs / 各厂商推送），仍不自建长连接 |
| 某模块 CPU 持续 > 70% | 优先做该模块缓存优化，最后才考虑拆服务 |
| 帖子/评论量级大导致热评排序变慢 | 热评进 Redis 缓存（ZSet） |
