### 缺口（按优先级）

**缺口 1（高）：资料类接口 5 个未实现** —— `UserController` 目前只有 #9 注销，缺：
- #10 我的资料 `GET /user/profile`
- #11 编辑资料 `PUT /user/profile`
- #12 更换手机号 `PUT /user/mobile`
- #13 修改密码 `PUT /user/password`
- #14 我的信息概览 `GET /user/summary`

前端 `pages/my/profile.uvue`、`settings.uvue` 页面已经画好了，联调时会出现"前端等接口"。特别注意：#12、#13 正是"高危操作清全部 token"规则的落点，`CHANGE_MOBILE` 短信场景现在发了验证码却没有任何接口消费它。

**建议做法**：在 `UserService/Impl` 里补 5 个方法，Controller 加 5 个端点。两个必须守的点：
1. #12、#13 成功后调 `tokenService.revokeAll(userId)`（和 `resetPassword` 里的写法一致）；
2. #12 要先校验新手机号未注册（复用 `getByMobile`），防换绑到已存在账号。

**验证方式**：改完用 Swagger 依次调 #10→#11→#13，每次改完密码拿旧 token 再请求一次 #10，必须返回 40101 才算对。

**缺口 2（中）：7 天注销清理定时任务未写** —— `job` 包目前只有二手超期下架一个任务（TradeItemExpireJob），注销清理还没有。注销到期后账号状态不会流转、数据不清理，`ban:user:{id}` 过期后此人还能被查到。

**建议做法**：Spring `@Scheduled` 每天跑一次，查 `status = DEACTIVATING 且 deactivate_deadline < now` 的用户做清理。坑点：启动类要加 `@EnableScheduling`，否则定时任务静默不跑；清理逻辑先只做"状态流转 + 软删"，物理清数据等真正有需要再说。

**缺口 3（中）：测试为零** —— 唯一测试类是 `contextLoads`。登录锁定、验证码错 5 次作废、白名单清 token 这些都是 Redis 时序逻辑，恰恰是最值得写单测的地方。

**建议做法**：优先给 `verifySmsCode`、`loginByPassword`（锁定的边界：第 5 次）、`TokenService` 三个类写单测，Redis 用内嵌或 Testcontainers。

### 顺手可改的小点（不紧急）

- `sms.minute-limit: 1` 配置写了但代码里写死 1 分钟，二选一，避免"假配置"误导后来人。
- `TokenService.issueAppToken` 每次签发都把整个白名单集合 TTL 重置为 30 天，旧 jti 会一直留在集合里（用户频繁登录时轻微膨胀）。1 万用户量级无碍，想更严谨可改成每个 jti 独立 key。
- `AuthInterceptor` 不校验 client 类型：现在 App token 能通过所有路径。**admin 模块落地时必须加"路径 /api/admin/v1/** 只认 ADMIN token"**，否则普通用户 token 可调后台接口。
- CORS `allowedOriginPatterns("*") + allowCredentials(true)` 开发期方便，上线前要收紧为真实域名。

## 二、任务模块

### 已完善的部分（不用动）

- #15 信息流：游标分页正确（多取 1 条判 hasMore，免 count），只查 `status=发布中`，软删除由 MyBatis-Plus 全局逻辑删除兜底，size 归一化（默认 20 / 上限 50）。

### 缺口（按优先级）

**缺口 1（高）：后台任务管理 #49 四个接口全部未实现**（发布 / 编辑 / 下架 / 软删）。后果：任务数据只能手插数据库，后台连发布入口都没有，任务模块没闭环。

**建议做法**（顺序有讲究，先 1 后 2）：
1. **先建管理员鉴权**：#47 管理员登录接口 + 用现有 `JwtUtil.createToken(id, CLIENT_ADMIN, jti)` 签发 2 小时 token + `AuthInterceptor` 增加 ADMIN 校验（可新建一个只挂 `/api/admin/v1/**` 的拦截器）。坑点：**不做这一步就直接写 #49，普通用户的 App token 也能调后台发布接口**——这是红线级漏洞。
2. 再写 `AdminTaskController` 四个端点，参数校验照文档：标题 ≤50 字、简述 ≤200 字、报酬说明 ≤100 字、deadline 必填、attachments 是 fileKey 数组。附件落 `t_media`（复用现有 `MediaService`，bizType=TASK）。删除必须是软删。

**验证方式**：Swagger 用管理员 token 走一遍"发布 → App 端 #15 能刷到 → 下架 → App 端 #16 返回 40401 → 删除 → 信息流不出现"。

**缺口 2（低）：任务表建了但无种子数据脚本** —— `schema.sql` 目前只有 t_user / t_task / t_media 三张表（其余表应是按周推进的欠账，不算本模块问题）。建议给 t_task 配一份种子 SQL（含已下架、软删的边界样例），联调时省得手插。
