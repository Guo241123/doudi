# 数据库设计（MySQL 8.0）

**依据**：需求文档 V1.4.1 ｜ **接口**：接口文档 V1.1（字段以此为准）｜ **架构**：模块化单体
**日期**：2026-10-10 ｜ **共 22 张表**

---

## 一、全局约定（每张表自动带上，下文不再重复）

| 字段 | 类型 | 说明 |
|------|------|------|
| id | BIGINT UNSIGNED | 主键，**自增**（游标分页依赖单调递增；单体不分库，不需要雪花 ID） |
| is_deleted | TINYINT | 软删除标记，0 正常 / 1 已删（**全库唯一允许的删除方式**） |
| create_time | DATETIME | 创建时间 |
| update_time | DATETIME | 更新时间 |

- 引擎 InnoDB，字符集 **utf8mb4**（昵称/内容含 emoji）；
- 命名蛇形小写；`LIKE` 是保留字所以点赞表叫 `like_record`；`user` 表在 SQL 中加反引号；
- 状态一律 TINYINT 或 VARCHAR 常量，与接口文档枚举一一对应；
- 手机号存原值但**查询展示层脱敏**，日志中禁止打印完整手机号。

## 二、user 模块（3 张）

### 1. `user` 用户

| 字段 | 类型 | 说明 |
|------|------|------|
| mobile | VARCHAR(11) | 手机号，**唯一索引 uk_mobile** |
| password_hash | VARCHAR(100) | 加盐哈希（BCrypt），非空 |
| nickname | VARCHAR(20) | 昵称，1～12 字 |
| avatar_key | VARCHAR(200) | 头像 fileKey（空=默认头像） |
| gender | CHAR(1) | M / F / U，默认 U |
| bio | VARCHAR(200) | 简介，可空 |
| status | TINYINT | 0 正常 / 1 封禁 / 2 注销处理中 |
| ban_reason | VARCHAR(200) | 封禁原因（可空） |
| deact_expire | DATETIME | 注销处理截止时间（可空） |

索引：`uk_mobile`；`idx_status`（后台筛封禁用户）。
说明：状态机 = 正常 → 封禁 → 正常；正常 → 注销处理中 →（7 天后定时任务）软删 + 清理。

### 2. `admin` 管理员

| 字段 | 类型 | 说明 |
|------|------|------|
| username | VARCHAR(50) | 登录名，**唯一索引** |
| password_hash | VARCHAR(100) | 加盐哈希 |
| nickname | VARCHAR(20) | 显示名（操作日志里显示这个） |

### 3. `sms_log` 短信发送记录

| 字段 | 类型 | 说明 |
|------|------|------|
| mobile | VARCHAR(11) | 接收手机号 |
| scene | VARCHAR(20) | REGISTER / LOGIN / RESET / CHANGE_MOBILE |
| code_hash | VARCHAR(64) | 验证码哈希（不存明文） |
| client_ip | VARCHAR(45) | 请求 IP（限频与审计） |
| sent_at | DATETIME | 发送时间，**索引 idx_mobile_sent(mobile, sent_at)** |

说明：限频实时判断在 Redis（计数器），本表是底账——Redis 丢了能重建，纠纷能对账。

## 四、trade 模块（2 张）

### 5. `trade_category` 分类

| 字段 | 类型 | 说明 |
|------|------|------|
| name | VARCHAR(10) | 分类名（≤6 字） |
| sort | INT | 排序（交易页 2×4） |
| icon_key | VARCHAR(200) | 图标 fileKey（可空） |

### 6. `trade_item` 二手物品

| 字段 | 类型 | 说明 |
|------|------|------|
| user_id | BIGINT | 卖家 |
| category_id | BIGINT | 分类 |
| title | VARCHAR(30) | 标题 |
| description | VARCHAR(500) | 介绍 |
| price_fen | INT | 价格（**分**，>0） |
| bargainable | TINYINT | 可议价 |

| status | TINYINT | 0 待审核 / 1 在售 / 2 已售 / 3 已拒绝 / 4 已下架 |

## 五、forum 模块（4 张）

### 7. `media` 通用媒体表（★ 跨模块复用）

| 字段 | 类型 | 说明 |
|------|------|------|
| biz_type | VARCHAR(20) | ITEM / POST / AVATAR / TASK / AD |
| biz_id | BIGINT | 所属业务 ID |
| media_type | TINYINT | 1 图片 / 2 视频 |
| file_key | VARCHAR(200) | OSS fileKey |
| sort | INT | 排序（轮播顺序） |
| audit_status | TINYINT | 0 待机审 / 1 通过 / 2 不通过 |

索引：`idx_biz(biz_type, biz_id, sort)`。
设计决策：**不用 JSON 列存图片列表**——机审状态要逐个管理、失败要定位重审，JSON 做不到；一张通用表让 OSS 清理、机审重试都有唯一入口。

### 8. `post` 帖子

| 字段 | 类型 | 说明 |
|------|------|------|
| user_id | BIGINT | 发布者（公告帖 = 管理员关联的固定账号或 admin_id） |
| content | VARCHAR(1000) | 文字 |
| status | TINYINT | 0 已发布 / 1 已删除 / 2 公告 |

索引：`idx_status_id(status, id)`（信息流游标 + 排除已删）、`idx_user(user_id, id)`。
说明：先发后审——没有待审核状态；"最新公告置顶"= 查询时取最新 ANNOUNCEMENT 单独置顶，不需要置顶字段。

### 9. `comment` 评论

| 字段 | 类型 | 说明 |
|------|------|------|
| post_id | BIGINT | 所属帖子 |
| user_id | BIGINT | 评论人 |
| content | VARCHAR(200) | 内容 |
| reply_to_id | BIGINT | 被回复评论 ID（可空；**只有两级**，回复的回复也指向根评论或被评论，前端拼"@xxx"） |
| like_count | INT | 点赞数冗余（避免每条评论 COUNT） |

索引：`idx_post_hot(post_id, like_count)`（热评 TOP3）、`idx_post_time(post_id, create_time)`（时间序游标）、`idx_user`。

### 10. `like_record` 点赞记录

| 字段 | 类型 | 说明 |
|------|------|------|
| user_id | BIGINT | 点赞人 |
| target_type | TINYINT | 1 帖子 / 2 评论 |
| target_id | BIGINT | 帖子或评论 ID |

索引：**`uk_user_target(user_id, target_type, target_id)` 唯一索引**（幂等兜底）+ `idx_target(target_type, target_id)`（查"谁赞过"）。
说明：点赞写流程 = Redis SET 判断 → 插 like_record（撞唯一索引即重复，静默返回成功）→ UPDATE 目标表 like_count。接口文档注记 2 的落地。

### 11. `favorite` 收藏

| 字段 | 类型 | 说明 |
|------|------|------|
| user_id | BIGINT | |
| target_type | TINYINT | 1 二手 / 2 帖子 |
| target_id | BIGINT | |

索引：`uk_user_target(user_id, target_type, target_id)` + `idx_user_id(user_id, id)`（我的收藏游标）。

## 六、message 模块（2 张）

### 12. `conversation` 会话

| 字段 | 类型 | 说明 |
|------|------|------|
| type | VARCHAR(20) | TASK_CONSULT / CUSTOMER / TRADE |
| user_id | BIGINT | 发起者（普通用户） |
| peer_id | BIGINT | 对方：TRADE=卖家 userId；TASK_CONSULT/CUSTOMER=管理员（存 admin_id，或统一约定 0 表示"管理员侧"） |
| task_id | BIGINT | 关联任务（仅任务咨询） |
| last_message | VARCHAR(200) | 最后一条摘要（冗余，列表页免联查） |
| last_time | DATETIME | 最后消息时间 |

索引：`idx_user(user_id, type, last_time)`（App 会话列表）、`idx_peer(peer_id, type, last_time)`（**后台工作台：任务咨询优先排序 = ORDER BY type, last_time**）、`uk_dedup`（发起去重：user_id + type + peer_id + task_id 组合唯一，空值用 NULL 处理注意）。

### 13. `message` 消息

| 字段 | 类型 | 说明 |
|------|------|------|
| conversation_id | BIGINT | 会话 |
| sender_id | BIGINT | 发送者（用户或管理员） |
| content | VARCHAR(500) | 内容 |
| read_time | DATETIME | 已读时间（空=未读；**未读数实时计数在 Redis**，进会话时置 Redis 并回填 read_time 兜底） |

索引：`idx_conv_id(conversation_id, id)`（会话内游标）。

## 十、表关系速查

```
user ──┬── trade_item ── trade_category
       ├── post ──┬── comment ←─ like_record（target_type=2）
       │          └── favorite（target_type=2）
       ├── favorite（target_type=1 → trade_item）
       ├── like_record（target_type=1 → post）
       ├── conversation ── message      （TRADE 会话 peer 指向另一 user）
       ├── report / blacklist / user_daily_active / analytics_event
       └── media（biz 指向 item/post/avatar）

admin ── task / operation_log / announcement(post, status=ANNOUNCEMENT) / conversation.peer
```

## 十一、设计决策注记

1. **自增主键而非雪花 ID**：单机单库，游标分页 `WHERE id < ? ORDER BY id DESC` 依赖单调递增，自增最简单；将来真分库再换分布式 ID（雪花也是趋势递增，游标逻辑不变）。
2. **通用 media 表而非 JSON 列**：机审状态逐文件管理、失败重审、OSS 清理都需要按行操作；JSON 列在这三件事上都是坑。
3. **计数冗余（like_count）+ Redis 未读数**：列表页绝对不做 COUNT 子查询；一致性靠"写时同事务更新 + 唯一索引防重"，丢计数可由 like_record 重算修复。
4. **公告不做置顶字段**：需求是"最新一条公告置顶"，查询时取最新公告即可，加字段反而要维护。
5. **user 表不用物理删除**：注销 7 天后做的是"清空个人信息字段 + 软删"，内容表（二手/帖子/评论）同步软删——举报追溯和平台合规取证依赖数据存在，只是不再关联到个人。
