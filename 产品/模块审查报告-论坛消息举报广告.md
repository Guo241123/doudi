## 一、拦截器重构复核（上轮 Bug 的修复验证）

上轮报告的"编辑二手被免登名单误伤"已修复，方案比建议的还干净：免登路径从 `WebMvcConfig` 挪进了 `AuthInterceptor`，拆成两张白名单——**游客只读表**（仅 GET 放行：任务/交易/论坛的列表详情评论）+ **游客可写表**（广告埋点上报，不限方法）。写方法一律要登录，从根上杜绝了"GET/PUT 共用路径被一起放行"这类坑。

复核结论：逻辑正确。建议你按这四条跑一遍回归确认：①物主 token 调 PUT /trade/items/{id} 能成功；②无 token 调它返回 40101；③游客 GET 详情正常；④无 token GET /user/profile 返回 40101（白名单外的方法不误放）。

### 缺口（按优先级）

**缺口 1（高）：拉黑过滤"三个口"全没做** —— 实现注记 3 要求信息流、评论列表、站内信三个查询口统一过滤黑名单；#29 要求"被拉黑作者的帖子对我返回 40401"。根因是拉黑模块（#43/#44）整个不存在，没有黑名单数据可查。

**建议做法**：等举报拉黑模块落地时一起做——三个查询口各加一次"我的拉黑名单 ID 集合"过滤（量小，服务层过滤即可），`requireVisiblePost` 里加"作者被 viewer 拉黑则 40401"。**注意别只做详情口，feed 漏过滤的话拉黑形同虚设。**

**缺口 2（中）：信息流广告混排未实现** —— #27 要求 itemType=POST/AD 混排，广告模块（#45）也是空的。前端 feed 渲染时广告位会缺席（任务页已留占位注释）。

**缺口 3（低，记欠账）**：①敏感词"词库后台可维护"未做（现内置 8 词 + 配置追加，够演示）；②公告只能手插数据库（发布入口在后台 #56）；③图片机审未接（media.auditStatus 硬编码通过，同交易模块，W5 一起还）。

## 三、消息 / 举报拉黑 / 广告埋点：整模块待建

三个模块都是"前端先跑、后端缺位"：

- **消息（#36～#40）**：会话复用（同类型同对象）、会话成员校验、进会话自动已读、未读数走 Redis 计数器（#40 配合 5s/30s 轮询）。需要建 t_conversation / t_message 表。
