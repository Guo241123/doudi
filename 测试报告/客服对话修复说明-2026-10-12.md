# 「联系卖家 / 客服对话」问题定位与修复说明

> 日期：2026-10-12 ｜ 范围：站内信（消息）链路
> 结论：**App 侧「联系卖家」双向对话本身是好的；真正缺的是"客服/任务咨询"的后台回复通道（接口文档 #55 后台站内信工作台），后端此前完全没实现 → 用户发出去的消息永远没人能回。已补齐并用 34 条用例验证闭环通过。**

---

## 一、先复现，再定位（不猜）

启动 Redis + 后端（8080），写专项脚本真实打接口，把三类会话全部跑一遍：

- **联系卖家（TRADE）**：买方发起 → 发消息 → 卖方能看到、能回 → 买方能看到回复 → 未读 +1/进会话清零 → 反向发起复用同一会话。**全部通过。**
- **任务咨询（TASK_CONSULT）**：发起带 taskId → 会话带 `taskRef{taskId,title}` → 发消息。**通过。**
- **客服（CUSTOMER）**：发起 → 用户发消息 → 会话列表里 peer = 社区管理员。**用户侧通过。**
- **拉黑拦截**：拉黑后发送返回 40301。**通过。**

结果：**用户→用户（联系卖家）没问题；用户→管理员（客服/任务咨询）没法形成闭环**——因为管理员那一侧根本没有接口。

> 说明：第一版脚本里"拉黑返回 500"是**脚本自身写错了路径**（把目标用户放进了请求体）。
> 真实路径是 `POST /blacklist/{userId}`（目标在 URL 上），前端 `api/report.uts` 写法正确，不是产品缺陷。

---

## 二、根因

对照文档与代码：

| 依据 | 内容 | 现状 |
|---|---|---|
| 接口文档 2.10 #55 | 「后台站内信工作台」：`GET /conversations`、`GET /conversations/{id}/messages`、`POST /conversations/{id}/messages`（管理员回复） | **后端完全没有** |
| MVP 开发顺序清单 W6 | 站内信完成标志 =「三类会话收发、**后台回复**、消息中心可见」 | 后台回复缺位 |
| 需求审查报告 决策记录 #1 | 站内信 MVP =「用户发文字消息，**管理员 Web 后台回复**」 | 同上 |

后台模块当时只有 `AdminAuthController`（#47 登录）和 `AdminTaskController`（#49 任务管理），**没有任何会话/消息接口**。
所以：客服、任务咨询会话的 peer 是管理员（`t_admin` id=1），而这套会话**只有 App 用户一侧能读写**，管理员无法查看、无法回复 → 用户永远收不到客服回音。

## 三、修复内容（后端）

新增/改动文件：

| 文件 | 说明 |
|---|---|
| `common/result/PageResult.java`（新增） | 后台列表统一用**页码分页**（文档 2.10 口径）；App 端继续用 `CursorResult` 游标分页，两套不混用 |
| `module/message/vo/AdminConversationVO.java`（新增） | 后台会话列表项：`conversationId / type / user{userId,nickname,avatarUrl} / taskRef / lastMessage / lastTime / unreadCount`。注意后台看的是"发起会话的 **App 用户**"，与 App 端看的"对方 peer"不是一个东西 |
| `module/message/controller/AdminMessageController.java`（新增） | `@RequestMapping("/api/admin/v1/conversations")`，三个端点，管理员 ID 一律从登录态取（不接收 adminId 入参） |
| `module/message/service/MessageService.java` | 新增 `adminConversations / adminMessages / adminReply` |
| `module/message/service/impl/MessageServiceImpl.java` | 三个方法实现 + `adminUnreadOf / requireConversation / markAdminRead` 私有方法 |

关键实现点：

1. **任务咨询优先排序**：`ORDER BY (type='TASK_CONSULT') DESC, id DESC`，用 `.last()` 承载整段排序（**不再调 `orderBy*`**，否则 MyBatis-Plus 会拼接到前面产生语法冲突）。
2. **管理员未读数**：一次分组查询统计"用户发来、`read_flag=0`"的条数；TRADE 会话是买卖双方的事、管理员不是参与方，不计入工作台未读。
3. **管理员进会话自动已读**：只把用户发来的消息置 `read_flag=1`，**不动 App 用户自己的未读计数器**（两边未读各自独立）。
4. **管理员回复**：以管理员身份写消息 + 更新会话摘要 + 给 App 用户（会话发起人）加 Redis 未读，用户端消息中心即可看到、未读角标 +1。为避免全表捞，未读聚合下推到 SQL。

### 现在怎么"以管理员身份回复客服"（暂时没有后台 Web 页面）

后台接口已就绪，先用命令行验证：

```bash
# 1) 管理员登录拿 token
curl -s -X POST http://localhost:8080/api/admin/v1/auth/login \
  -H "Content-Type: application/json" \
  -d '{"username":"admin","password":"<管理员密码>"}'

# 2) 看会话列表（任务咨询优先）
curl -s "http://localhost:8080/api/admin/v1/conversations?page=1&size=20" \
  -H "Authorization: Bearer <上一步的 token>"

# 3) 回复某个会话（把 <id> 换成会话 ID）
curl -s -X POST http://localhost:8080/api/admin/v1/conversations/<id>/messages \
  -H "Authorization: Bearer <token>" -H "Content-Type: application/json" \
  -d '{"content":"您好，请描述一下具体问题"}'
```

回复后回到 App 消息中心，客服会话未读会 +1，点进去就能看到管理员的回复。
